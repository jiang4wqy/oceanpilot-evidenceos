# 拒付(Chargeback)申诉智能体 —— 数据需求说明(对内)

> 用途:交付给公司内部风控 / 合规 / 运营 / 支付同事,说明我们需要哪些数据、以什么形式、以及**必须遵守的脱敏红线**。
> 版本:2026-08-07。对应工程 issue #21(T12 数据导入)。

---

## 一、一句话背景

我们在做一个**跨境拒付申诉的多智能体系统**:商户描述问题 → 系统判定拒付理由 → 逐项提示补齐证据 → 给出"是否达标 / 胜诉概率 / 应由哪个团队处理 / 申诉时限" → **人工确认后**再对外提交。

系统的判断由一个**确定性内核**(规则表)做出,AI 只负责解释和提示,最终由人拍板。**这个内核目前用的是我们自己编的占位规则,要变成"真的能用",就需要把公司现有的拒付处理经验(理由码规则、各行/卡组织的证据要求、历史结果)结构化地喂进去。**

> ⚠️ **最重要的一条:全程只接受脱敏 / 合成数据。系统永远不碰真实持卡人信息,也永远不执行任何支付/退款/风控放行操作,最强动作只是"建议人工复核"。** 详见第四节红线。

---

## 二、我们需要的三类数据(按优先级)

### 数据一:拒付理由码规则表 ★★★(最高优先级,先给这个)

这是内核的"大脑"。**它决定了:一笔拒付属于哪一类、要哪些证据、归谁处理、多少天内要申诉完、是不是高风险。**

我们内部把拒付归成 **7 个理由族**(见附录 A)。你们日常用的是卡组织的**原始理由码**(如 Visa `10.4`、Mastercard `4837`、`13.1` 等)。**我们最需要的,就是你们把常见的原始理由码,按下面这张表映射并补全:**

| 需要提供的字段 | 说明 | 示例 |
|---|---|---|
| 卡组织原始理由码 | 你们系统里实际出现的码 | `Visa 13.1` / `MC 4855` |
| 卡组织 | 属于哪个网络 | `VISA` / `MASTERCARD` / `AMEX` … |
| → 归入我们的理由族 | 从附录 A 的 7 个里选 | `PRODUCT_NOT_RECEIVED` |
| 责任团队 | 通常由哪个团队主办申诉 | `CUSTOMER_SUPPORT`(见附录 C) |
| 申诉时限(天) | 从收到拒付到必须提交举证的天数 | `15` |
| 是否高风险 | 是否需要强制人工复核 | 是 / 否 |
| 所需证据清单 | 每条:证据类型 + 权重(1–10)+ 是否关键 | 见下 |

"所需证据清单"里的每一项:

| 字段 | 说明 | 示例 |
|---|---|---|
| 证据类型 | 从附录 B 的证据码里选 | `fulfillment.proof_of_delivery`(签收证明) |
| 权重 | 该证据对胜诉的重要性(1–10) | `3` |
| 是否关键 | 缺了它基本必败/必须人工复核 | 是 |

> 📌 **如果连结构化都来不及做:** 直接把你们现有的《拒付举证 SOP / checklist / 各理由所需材料清单》原样发来(文档、表格、甚至截图都行),**结构化的活我们来做**,再回给你们确认。

---

### 数据二:银行 / 卡组织专属证据模板 ★★(次高)

同一个拒付理由,不同**发卡行 / 收单行 / 卡组织**对材料的要求和顺序可能不同(例如某行要求"签收证明"排在最前、举证窗口更短)。有这层数据,系统能针对具体银行给更精准的提示。

| 字段 | 说明 | 示例 |
|---|---|---|
| 理由族 | 附录 A | `PRODUCT_NOT_RECEIVED` |
| 卡组织 | | `VISA` |
| 规则来源 | `bank`(银行专属)或 `network`(卡组织通用) | `bank` |
| 银行标识 | 若是 bank 规则,用**内部代号/化名**,不要真实全称也行 | `BANK_A` |
| 所需证据 | 证据码列表(附录 B) | `[proof_of_delivery, tracking, receipt]` |
| 提交顺序 | 证据码的推荐排列(必须是"所需证据"的一个排列) | `[proof_of_delivery, tracking, receipt]` |
| 举证窗口(天) | | `12` |
| 备注 | 可选,**不得含敏感信息** | "该行要求签收证明置顶" |

> 这块**可以后给**。没有它系统会退回到"数据一"的通用规则,不影响主流程。

---

### 数据三:历史案例样本(用于调优与评测)★(锦上添花)

用来校准胜诉概率、优化 AI 的提示质量、做离线评测。**必须彻底脱敏或直接用合成/聚合数据。**

| 字段 | 说明 | 示例 |
|---|---|---|
| 案例编号 | **化名**,与真实工单号无对应关系 | `SYN-CASE-0001` |
| 理由族 | 附录 A | `FRAUD_CARD_NOT_PRESENT` |
| 当时具备的证据 | 证据码列表(只要"类型",不要内容) | `[receipt, threeds]` |
| 结果 | `won` / `lost` / `pending` | `lost` |
| 备注 | 可选,**禁止任何 PII** | "缺 3DS 关键证据,败诉" |

> 💡 **强烈建议给"聚合统计"而非逐个真实案例**,例如:"过去 12 个月,`PRODUCT_NOT_RECEIVED` 类拒付,证据齐备时胜诉率约 70%,缺签收证明时约 20%"。这类统计既安全,对我们调参又最有用。

## 三、格式与交付

- **格式:** JSON 或 Excel/CSV 均可,我们会随本文附上**空白模板**;每类数据一个文件。
- **合成 JSON 模板:** 见 [`docs/data/templates/`](templates/),包含理由码映射、内部理由策略、银行/卡组织规则和案例样本四个文件。
- **收到文件后的校验:** 安装项目后运行 `oceanpilot-validate-data`;成功时只输出各类记录数量,失败时返回固定错误,不会回显原始记录。
- **数量:** 数据一先覆盖**最高频的 5–10 个理由码**即可,不必一次给全。
- **交付渠道:** 走公司内网 / 加密方式;**不要贴进公开聊天、邮件正文或代码仓库**。
- **约束提醒:** 理由码 / 证据码 / 团队都是**封闭取值**(见附录),不在清单内的值会被系统拒收——遇到对不上的,请标出来,我们一起决定是加映射还是扩枚举。

## 四、脱敏红线(请逐条确认后再发)⛔

**绝对不能出现在任何一份数据里:**

- 卡号(含仅做掩码但仍可还原的)、CVV/CVC、有效期
- 持卡人 / 消费者姓名、地址、邮箱、电话、身份证 / 护照 / 税号
- 真实交易流水号 / 订单号 / 工单号(请用化名编号)
- IP 地址、设备指纹原值
- 商户 API Key / Secret / Token、内部系统凭证、任何密钥

**我们只需要"类别 / 枚举 / 是否具备 / 聚合计数",不需要证据的具体内容。**
例:我们要知道"这个案子**有没有**签收证明",**不要**签收证明扫描件本身;要知道"胜诉率 70%",**不要**具体是哪几笔。

**发送前自检(全部为"是"才发):**
- [ ] 没有任何一个字段能定位到真实的人 / 卡 / 单?
- [ ] 编号都是化名,和真实系统无可逆对应?
- [ ] 备注里没有粘进原始文本 / 邮件 / 聊天记录?
- [ ] 没有任何密钥、token、内部链接?

## 附录 A:理由族枚举(7 个,封闭取值)

| 取值 | 含义 |
|---|---|
| `FRAUD_CARD_NOT_PRESENT` | 无卡欺诈(CNP fraud) |
| `PRODUCT_NOT_RECEIVED` | 未收到商品 / 服务 |
| `PRODUCT_NOT_AS_DESCRIBED` | 商品与描述不符 / 质量问题 |
| `DUPLICATE_PROCESSING` | 重复扣款 |
| `CREDIT_NOT_PROCESSED` | 退款未入账 |
| `SUBSCRIPTION_CANCELED` | 已取消订阅仍被扣费 |
| `AUTHORIZATION_ERROR` | 授权错误 |

## 附录 B:证据码枚举(15 个,封闭取值)

| 取值 | 含义 |
|---|---|
| `transaction.receipt` | 交易收据 / 凭证 |
| `auth.avs_result` | AVS 地址验证结果 |
| `auth.cvv_result` | CVV / CVC 校验结果 |
| `auth.threeds` | 3DS 认证结果 |
| `auth.device_ip_match` | 设备 / IP 匹配 |
| `fulfillment.tracking` | 物流跟踪号 / 轨迹 |
| `fulfillment.proof_of_delivery` | 签收证明 |
| `fulfillment.address_match` | 收货地址匹配 |
| `product.description` | 商品描述 |
| `billing.refund_record` | 退款记录 |
| `policy.terms_refund` | 服务条款与退款政策 |
| `comms.customer` | 与客户的沟通记录 |
| `subscription.cancellation_record` | 订阅取消记录 |
| `history.prior_transactions` | 历史交易记录 |
| `billing.duplicate_check` | 重复扣款核查记录 |

## 附录 C:责任团队枚举(6 个,封闭取值)

| 取值 | 含义 |
|---|---|
| `BUSINESS` | 业务 / 商务 |
| `TECHNICAL_SUPPORT` | 技术支持 |
| `RISK` | 风控 |
| `FINANCE` | 财务 |
| `CUSTOMER_SUPPORT` | 客服 |
| `PSP_SUPPORT` | 支付 / PSP 支持 |

## 附录 D:一条完整示例(数据一,JSON)

```json
{
  "reason_code": "PRODUCT_NOT_RECEIVED",
  "responsible_team": "CUSTOMER_SUPPORT",
  "default_deadline_days": 15,
  "high_risk": false,

    {"evidence_code": "transaction.receipt", "weight": 1, "critical": false},
    {"evidence_code": "fulfillment.tracking", "weight": 3, "critical": true},
    {"evidence_code": "fulfillment.proof_of_delivery", "weight": 3, "critical": true},
    {"evidence_code": "fulfillment.address_match", "weight": 2, "critical": false},
    {"evidence_code": "comms.customer", "weight": 1, "critical": false}
  ]
}
```

> 收到数据后,我们会用严格校验器逐条导入(未知取值 / 缺字段 / 含敏感信息一律拒收并回报),再回给你们一份"已导入 / 被拒原因"清单确认。
