# OceanPilot 开题报告补充材料｜内容源

> 本文件是两页 PDF 的文字单一事实源。当前比赛原型使用合成数据，已打通支付异常的建案、补证、诊断、责任建议、人工确认审计与只读 Cockpit；不连接生产系统或执行资金动作。

## Page 1｜01 为什么不是“再做一个 Agent”

### 一句话主张

OceanPilot 不抢着回答，而是先把一次跨境支付问题组织成可追溯案件：缺证先补问，过门再判断，高风险动作由人工确认。

### 外部证据

1. **结构化缺口：** Swift 2025 研究显示，跨境支付异常调查消息中，超过 `72%` 的数据字段仍为自由文本。
2. **单点能力已成熟：** Stripe 已按地区、币种和金额动态选择支付方式；Primer 已用事件时间线还原请求与响应。
3. **协作仍需人工还原：** 一位 G2 验证用户指出，历史交易与到账关系仍需人工梳理。这是定性个案，不代表行业比例。

### 我们的判断

推荐与时间线解决了局部效率，却没有自动形成跨角色可交接的证据口径。OceanPilot 因此把上下文、时间线、来源、版本和责任状态放进同一份“商户成功案件”。这是基于上述来源形成的方案推论，不是外部统计原句。

### 三个核心设计

| 设计 | 作用 |
|---|---|
| 商户成功案件 | 聚合问题上下文、证据、判断与交接状态 |
| 案件证据契约 | 约束来源、时间、版本与引用；缺证时禁止直接猜测 |
| 受控协作闭环 | AI 处理模糊表达，规则约束状态与责任，高风险动作人工确认 |

### 当前闭环图

PDF 构建器原生绘制七步 synthetic 闭环：问题建案 → 证据缺口 → 角色化补问 → 确定性诊断 → 责任建议 → 人工确认 → 只读 Cockpit。人工确认只写 approval audit，不执行业务动作。

## Page 2｜02 支付异常闭环已打通，综合智能体按阶段扩展

### 当前运行架构图

PDF 构建器原生绘制五层当前运行架构：飞书交互 → 案件编排 → 诊断内核 → 受控协作 → 持久化展示。当前诊断 API 已接入四条确定性规则；飞书 callback、七步补证、自动诊断、人工确认审计和 Cockpit 已由本地测试及签名 fixture 验证。

仓库中的 `fig-02-layered-architecture.png` 是 Foundation 阶段历史快照，不嵌入当前 PDF。

### 三状态能力矩阵

| 状态 | 内容 |
|---|---|
| 当前已实现 | synthetic 建案、七步补证、四条确定性规则、持久化诊断、证据引用、责任建议、飞书人工确认审计和只读 Cockpit；`8` 条 OpenAPI 路径 |
| 本地演示保障 | 签名 callback fixture 完成消息到确认的同一业务链；PowerShell fallback 覆盖四条规则；最终测试数见 PR4 checkpoint |
| 尚待外部验证/规划 | 真实飞书测试群、远端 CI 与匿名最新提交需外部证据；真实只读适配、Workflow、工单/SLA、知识复用和运营看板仍为规划能力 |

### 试点目标

- 证据引用率与高风险动作人审率：`100%`（设计硬约束）
- 资料到齐时间：缩短 `30%`
- 首次责任域命中率：达到 `80%`
- 案件改派次数：降低 `30%`
- 同时跟踪人工升级率与重复问题复用率

以上均为以企业现有流程为基线的试点目标，不是当前已实现收益。

### 四阶段落地路线

1. **比赛演示（当前）：** 使用 synthetic 数据展示飞书协作与支付异常全链，所有结论均可回到持久化证据。
2. **真实飞书 smoke：** 在测试租户和公网 HTTPS callback 下完成一次带时间证据的群聊演示。
3. **真实只读适配：** 在企业授权下接入订单、3DS、回调、风控、退款和报表查询，不引入资金执行器。
4. **试点评估：** 校准规则、完成场景验收，并按试点指标比较前后流程。

### 公开验证边界

- 当前不声称生产就绪、远端 CI 绿色、真实飞书群联调通过或真实业务成效。
