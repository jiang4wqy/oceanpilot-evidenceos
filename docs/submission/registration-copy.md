## Part 1｜命题前置分析与洞察（50-300字）

<!-- PART1_START -->
Swift 2025研究显示，跨境支付异常调查消息中，超过72%的数据字段仍为自由文本。Stripe已按地区、币种和金额动态选择支付方式，Primer也用事件时间线还原请求与响应；一位G2验证用户却指出，数据虽在，历史交易与到账关系仍需人工梳理。这提示单点推荐和时间线尚未解决跨角色证据交接。OceanPilot因此以“商户成功案件＋证据契约”统一上下文、时间线和来源：缺证先补问，达到证据门槛后才输出带引用的候选原因，再由规则和人工完成责任路由。

## Part 2｜整体解决方案设计（300-600字）

<!-- PART2_START -->
1.【方案概述】OceanPilot不是问答机器人，而是证据驱动的综合商户成功智能体。它围绕同一份“商户成功案件”组织资料、判断与交接，目标覆盖接入前建议与上线后的支付异常、拒付、退款和对账协作。

2.【架构与模块】系统由交互入口、案件证据中枢、确定性诊断/路由、受控智能体和审计存储组成。商户或OP描述问题后，系统自动建案并向正确角色补问；证据达标后才输出带引用的候选原因、置信度、责任域和下一动作。高风险建议必须人工确认，确认与业务执行分离。

3.【当前证据】比赛仓库已打通两个本地synthetic纵向切片：支付异常支持四类规则场景、持久化诊断、支付cockpit及经真实签名校验的飞书本地fixture；拒付支持原因识别、补证、胜诉评估、打包、申诉草稿、人工门和审计。8月16日展示先聚焦支付异常，再用拒付说明架构可扩展。

4.【创新与价值】区别于普通问答和看板，本方案让判断绑定证据来源、时间、版本与引用；AI理解模糊表达，规则守住门槛和路由，人类控制高风险动作。试点将跟踪资料到齐时间、责任域命中率、改派次数与人工升级率，当前尚无实测结果。

5.【边界与推广】当前只用合成数据，不连接Oceanpayment生产系统或真实飞书群，不执行支付、退款、风控放行、资金移动、生产配置变更或真实上游提交。后续在授权下接入只读数据、完成真实群联调和生产安全验收，再扩展至更多商户成功场景。
<!-- PART2_END -->

## 当前事实边界

- 已验证两个 synthetic 纵向切片：支付异常协作与拒付申诉。
- 支付诊断 API 返回真实持久化结果；当前 OpenAPI 实际为 19 条 paths。
- signed local Feishu fixture 已验证签名、补证、诊断、人工确认审计和 replay；真实飞书测试群尚未验证。
- 拒付上游只使用 synthetic mock，不代表银行、卡组织或 Oceanpayment 真实提交。
- 不写固定总测试数；以目标提交的实际测试和 CI 为准。
- 当前不含真实商户/交易数据，不声明生产就绪、实测商业效果或 Gate 4 PASS。
