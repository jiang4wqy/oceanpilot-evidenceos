# OceanPilot 开题报名提交包设计

**日期：** 2026-07-19

**提交截止：** 2026-07-19 24:00（北京时间）

**内部提交目标：** 20:30 前完成表单提交，至少保留三小时缓冲
**批准策略：** B——报名文案 + 公开 GitHub + 两页 PDF + 可验证视觉证据

## 1. 目标

本轮不继续扩展后端功能，而是把已经通过验证的本地基础原型整理成评委可快速理解、可匿名访问、可复核的开题提交包。提交必须同时满足三点：

1. 直接表达 OceanPilot 的核心判断与新颖点，不复述企业命题；
2. 明确区分“当前已实现的合成数据基础原型”和“入围后的完整飞书方案”；
3. 用 GitHub、两页 PDF、架构图和本地验证结果形成证据链。

## 2. 非目标与事实边界

截止前不实施诊断持久化、`CaseService.diagnose()`、飞书 Agent、A2A、MCP、Oceanpayment 真实接口、工单、SLA、知识库、看板、鉴权、远程 CI 或部署。不得声称：

- 当前已经实现智能诊断或 AI/LLM 运行时；
- 当前已经接入飞书或 Oceanpayment 数据；
- 已取得真实商户反馈或业务改善指标；
- 项目已经生产就绪；
- 通用工程方法或第三方依赖是团队独创算法；
- 公开仓库等于开源项目。仓库不创建 `LICENSE`，材料中不使用“开源”表述。

诊断 HTTP 路径当前固定返回 `501 FEATURE_DEFERRED`。它必须被描述为诚实的里程碑边界，不能包装成已完成能力。

## 3. 核心传播主张

OceanPilot 的主张不是“再做一个聊天机器人或数据看板”，而是建立一个 AI 与人工都必须遵守的商户成功协作协议：

> 把一次跨境支付问题组织成版本化案件，把每个判断绑定到结构化证据；资料不足时先定位缺口并向正确角色补问，资料满足最低条件后才输出带来源、可信度、责任域和下一动作的候选原因。

对外只保留三个新颖点：

1. **商户成功案件（Merchant Success Case）**：用一个持续演进的案件聚合订单、风险、回调、退款、报表与协作状态，替代散落截图和聊天记录。
2. **案件证据契约（Case Evidence Contract）**：证据类型、来源、时间、可靠性、版本和引用均受约束；缺证时 AI 必须补问，不能直接猜测。
3. **受控协作闭环**：AI 处理语义、补问和候选原因，确定性规则负责状态、路由和人审门；高风险动作始终由人工确认。

## 4. 摘要生成方法

组合使用从 `shawnpang/startup-founder-skills` 单独安装并完成安全审查的两个内容型技能：`accelerator-application` 负责 Part 1 / Part 2 的一句话定位、问题、机制、实证和独特洞察；`pitch-deck` 负责 PDF 与图示的“痛点 -> 方案 -> 证据 -> 价值”叙事弧、结论式标题和评委视角复核。两者均限定为 `content-only`：不读取 `.agents/startup-context.md`，不调用关联技能，不生成融资、市场规模或募资内容，不复用示例数字，也不执行上传、发布或表单提交。

采用四段压缩逻辑：

```text
结构性矛盾 -> 核心判断 -> 解决机制 -> 可验证价值
```

技能只提供以下约束：主张先行、先写已经完成的工作、每个事实有来源、方法与贡献分离、数据替代形容词、禁用空泛开场、检查字数和逻辑跳跃。最终文案必须经过独立“题目复述率、创新辨识度、事实边界、字符数”审查。

### 4.1 Part 1：命题前置分析与洞察

- 表单限制：50–300 字；内部目标：220–270 个字符。
- 首句直接给出结构性判断，不写“随着全球化发展”“本题要求”“我们注意到”等开场。
- 只使用一组企业规模事实，避免堆数字。
- 不展开具体 Agent、MCP 或技术架构。
- 必须解释为什么普通 FAQ、静态国家表或通用聊天机器人不足。
- 结尾落在“统一案件、统一证据、统一判断口径”的机会，不复述题目列举的五项功能。

推荐论证顺序：

1. 支付方式和异常判断同时受国家、币种、业务形态、通道与异步状态影响；
2. 一次问题的事实分散在订单、风险、3DS、回调、退款、报表和日志；
3. 核心瓶颈是证据无法被快速还原、归因和交接；
4. 因此需要证据驱动的商户成功案件，而不是另一个信息入口。

### 4.2 Part 2：整体解决方案设计

- 表单限制：300–600 字；内部目标：480–560 个字符。
- 首句必须在 45 字内说清“OceanPilot 是什么”和“与常规 Agent 的区别”。
- 正文只讲一条主链：受理建案 -> 缺口补问 -> 受控取证 -> 候选诊断 -> 人审路由 -> 知识复用。
- 三个创新点只出现一次，避免用不同术语重复同一概念。
- 明确写出当前原型实证：案件/证据基础链、SQLite 原子事务、严格校验、审计边界、`717 passed`、本地演示。
- 将飞书 Agent、A2A/MCP、真实适配器和诊断编排写成“入围后的落地路径”，不能使用完成时。
- 业务价值写成“试点验收指标或目标”，不写成已经发生的收益。

试点价值指标限定为：资料到齐时间、首次责任域命中率、改派次数、人工升级率、重复问题复用率；证据引用率与高风险动作人审率作为设计硬约束。目标百分比只有在明确标注“试点目标”时才能出现。

## 5. 可验证能力矩阵

| 状态 | 可公开内容 |
|---|---|
| 已实现 | `GET /health`；案件创建/读取；证据首次写入、重放和冲突；严格 UUIDv4/RFC3339/闭合 DTO；readiness 与下一补问基础；SQLite 原子事务、revision 与审计；敏感输入安全失败；本地 `717 passed`、Ruff、compileall、五路径 OpenAPI 和演示通过 |
| 离线领域资产 | 四条确定性支付异常规则及领域测试，可生成证据引用、置信度、人审原因、责任团队与下一动作；尚未接入 HTTP 诊断主链 |
| 设计完成、待接入 | 诊断快照持久化、真实诊断 API、飞书 Agent、A2A/MCP、工单/SLA、知识库、运营看板、三个 synthetic 诊断闭环 |
| 不作声明 | 真实 Oceanpayment 数据、真实业务成效、生产安全、远程 CI、自动支付或退款动作 |

材料中关于审查的准确说法为“通过独立审查与控制端复验”，不得泛化成未经记录的“多轮独立审查”。

## 6. 视觉资产设计

用户使用 Image 2 生成视觉资产，总控提供精确提示词并在回传后执行文字、流程、品牌和事实审查。所有图统一使用白色背景、深海军蓝、海洋蓝、青绿色，琥珀色只表示人工复核，绿色表示当前已运行，浅灰表示规划中。禁止官方 Logo、卡号、真实商户信息、伪造数据看板和无法验证的百分比。

### 图 1：Evidence-First 核心闭环

- 比例：16:9，横向矢量信息图。
- 目的：一眼说明创新机制，不画普通线性聊天流程。
- 主链：问题建案 -> 证据缺口 -> 角色化补问 -> 只读取证 -> 候选原因与置信度 -> 人审/路由 -> 知识复用。
- 中心必须是持续存在的“商户成功案件 + 证据契约”，各步骤围绕它更新。
- 用途：PDF 第 1 页主图；可复用到 README。

### 图 2：当前原型与完整方案的分层架构

- 比例：16:9，横向分层架构图。
- 四层：飞书交互与 Workflow；OceanPilot Case/Evidence/Diagnosis；只读适配器与 MCP；Oceanpayment/知识/工单数据源。
- 状态编码：绿色实线表示当前运行的 FastAPI/CaseService/Domain/SQLite；黄色虚线表示离线规则资产；灰色虚线表示飞书、MCP、真实数据与诊断编排规划。
- 用途：README 主架构图；PDF 第 2 页。

### 图 3：人工协作 Before / OceanPilot After

- 比例：16:9，左右对比信息图。
- Before：截图、订单号、错误码、报表和日志分散，多角色反复转发，判断口径不一致。
- After：所有角色围绕同一案件补证，AI 只在证据门通过后给候选原因，Workflow 执行确定性路由，人工确认高风险动作。
- 用途：PDF 第 1 页辅助图；时间不足时可取消，不阻塞提交。

Image 2 输出以 PNG 原图回传。若图中文字出现乱码、错词、额外标签或事实错误，总控不得直接使用；优先要求重新生成，其次使用无文字底图并在 PDF 排版层叠加中文标签。

## 7. 两页 PDF

文件名：`OceanPilot-开题报告补充材料.pdf`。

### 第 1 页：为什么是“证据闭环”

- 一句话主张；
- 三条外部研究事实；
- 图 1 为主，图 3 为辅；
- 三个创新点；
- 不出现技术文件列表或大段正文。

### 第 2 页：如何落地且已经证明了什么

- 图 2 分层架构；
- 已实现 / 离线资产 / 下一阶段三状态表；
- 本地验证摘要：`717 passed`、五条 API、本地演示、独立审查与控制端复验；
- 试点指标与四阶段落地路线；
- GitHub URL 与二维码只在匿名验证成功后加入。

PDF 必须在 100% 缩放下可读，不能依赖附件外部链接才能理解。所有来源在页脚用短链接或编号列出。

## 12. 验收标准

1. Part 1 在 50–300 字内，Part 2 在 300–600 字内；字符数由脚本和人工双检。
2. 两段文案首句均不复述命题，不出现空泛开场；评审者在 15 秒内能指出三个新颖点。
3. 每个企业或行业事实均可追溯到 `docs/submission/sources.md` 的真实链接。
4. “已实现、离线资产、规划中”三种状态在 README、PDF 和表单中完全一致。
5. GitHub public 且匿名可访问，提交范围无 secret、数据库、日志和临时文件。
6. PDF 恰好两页、文字清晰、图文一致、来源可读。
7. 至少图 1、图 2 完成事实审查；图 3 为非阻断可选项。
8. 最终报名材料不声称当前诊断、飞书集成、真实业务成效或生产就绪。
