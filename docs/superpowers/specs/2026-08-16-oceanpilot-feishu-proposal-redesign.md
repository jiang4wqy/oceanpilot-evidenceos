# OceanPilot 40 强飞书参赛方案叙事化重构设计

日期：2026-08-16
状态：已获用户书面批准，飞书正文已实施
适用范围：40 强正式飞书云文档；本轮不修改产品代码

## 1. 目标

把现有“材料齐全但像评分答题卡”的方案，重构为一份评委愿意连续读下去的企业项目说明书。

文档必须让评委依次形成四个判断：

1. 这是一个值得解决的跨境支付商业问题；
2. OceanPilot 提出的不是普通客服机器人，而是一套可治理的 Agent 协作系统；
3. 团队已经用拒付申诉打通了一条可验证的标杆链路；
4. 同一底座有清晰的企业试点与全生命周期推广路径。

统一定位为：

> **OceanPilot：AI 驱动的跨境支付全生命周期商户成功智能体**
> 从支付问题理解、证据补全、规则判断到人工治理的一体化 Agent 协作平台

拒付申诉是本次展示的高复杂度标杆链路，不是产品边界。

## 2. 读者与阅读节奏

主要读者是需要在线独立浏览飞书文档的比赛评委。设计按三个阅读层次展开：

- **60 秒：** 看懂问题、方案、Demo、价值和当前边界；
- **5 分钟：** 顺着一条拒付案件理解完整产品逻辑；
- **深入核验：** 查看 AI 架构、测试、规则、审计和参考资料。

每个章节只承担一个主要问题。章节开头先给结论，再给解释和证据；避免连续长段、连续表格和同类信息重复出现。

## 3. 已选择的设计方向

采用“叙事型项目说明书”，不采用以下两种结构：

- 不采用四项评分各自成章的答题卡结构，因为它会割裂产品故事；
- 不采用技术白皮书结构，因为它会把商业价值和实际使用体验压到后面。

官方评分维度仍全部覆盖，但自然嵌入项目叙事：

- AI 应用创新性由“问题定义、证据契约和治理机制”体现；
- 业务价值由“协作链路、试点指标和 ROI 方法”体现；
- AI 应用深度由“Agent、模型、工具、规则、降级和人工闸门”体现；
- 完整度、落地性与推广性由“真实 Demo、工程证据和四阶段路线”体现。

文档开头保留一个轻量“评委阅读导航”，只用四个短结论卡指出证据位置，不再使用评分映射表。

## 4. 新正文结构

### 封面｜先建立项目级别

- 正式项目名与副标题；
- 一句话价值：把分散的支付问题变成有证据、有规则、有人负责、可审计的案件；
- 三个短标签：证据驱动、规则可追溯、人工治理；
- Synthetic / Mock 数据边界用一行浅色说明呈现，不抢夺主视觉。

### 1. 执行摘要｜为什么值得继续读

用三段完成“问题—方案—本次证明”：

1. 跨境支付企业面对的是跨系统、跨角色、跨规则的协作问题；
2. OceanPilot 用统一案件协议组织 AI、确定性系统和人工；
3. 本次用拒付申诉证明从自然语言受理到审计闭环的标杆链路。

结尾放四个评委导航卡，每张只有“核心结论 + 对应章节”。

### 2. 商业问题｜为什么普通客服和工单不够

从一名商户描述“为什么付款失败 / 为什么发生拒付”开始，展示信息如何跨商户、客服、技术、风控、争议运营、银行和卡组织流动。

本章只保留四个结构性矛盾：事实分散、证据标准不统一、规则与责任不稳定、高风险动作难治理。最后自然引出“先建立共同事实，再让 AI 参与判断”。

### 3. OceanPilot 方案｜一个入口、一份案件、七个能力环节

先给完整产品全景，再解释：

**问题理解 → 版本化案件 → 证据补全 → 规则判断 → 责任路由 → 人工确认 → 审计沉淀**

支付失败、3DS/callback、风控、拒付、退款、对账、配置与上线共享底座，仅替换证据政策、规则库和责任路由。

### 4. 标杆 Demo｜跟随一条案件看系统如何工作

这是正文中心章节，不再把截图集中堆叠。按照用户视角分成五幕：

1. 商户自然语言描述异常，系统创建 Synthetic 案件；
2. 系统发现缺证并进行角色化补问；
3. 证据达标后执行确定性判断和责任路由；
4. 判断与材料包引用同一规则版本；
5. 高风险动作等待人工确认，形成 Mock 回执和审计。

每一幕使用“动作说明 → 真实截图 → 这张图证明什么”的顺序。截图图注不复述界面，只说明其证明责任和边界。

### 5. AI 深度｜AI 如何进入业务判断而不越权

用三层纵向结构替代职责表：

- **AI / Agent：** 理解、提取、补问、解释和起草；
- **确定性内核：** 版本、证据门槛、规则、状态机、幂等与审计；
- **人工：** 处理模糊、冲突、低置信度和高风险动作。

随后解释 ModelProvider、Agent 编排、工具调用、失败降级和 AI 判断总结。核心结论是：AI 参与过程，但不能修改事实、规则和审批门槛。

### 6. 创新性｜创新发生在决策过程，而不是 Prompt 数量

围绕六个机制展开：版本化案件、案件证据契约、缺证停止、规则版本引用、人工闸门、审计资产。

对比图只承担一个任务：说明普通 AI 客服、传统工单与 OceanPilot 的目标不同。图后用一段话收束，不再重复前文。

### 7. 业务价值｜如何判断协作真的变短

先按商户、运营团队、风险治理和平台能力讲四层价值，再给试点验证方法。

原试点指标表改为六个连续指标卡：

- 资料到齐时间；
- 首次责任域命中率；
- 案件改派次数；
- 证据引用覆盖；
- 高风险动作人审覆盖；
- 超期案件比例。

每张卡固定三行：为什么重要、试点目标或硬约束、如何测量。30% 和 80% 必须标记为试点目标，100% 必须标记为系统设计硬约束。

### 8. 落地与推广｜从比赛原型到企业受控运行

使用四阶段故事线：比赛原型、Oceanpayment 授权影子运行、受控系统接入、全生命周期平台。每一阶段都说明数据范围、允许动作、验证指标和升级条件。

### 9. 工程可信度与安全边界｜哪些已经证明，哪些仍在推进

原状态表改成四个状态区：

- 已实现 / 已验证；
- 当前原型；
- 企业试点目标；
- 后续路线图。

固定提交、CI、测试数量、公开仓库和飞书协作台作为核验入口。DeepSeek 在固定提交、测试、脱敏边界和真实运行证据齐备前，不写成已完成在线接入。

### 10. 结语与下一步｜给评委一个明确记忆点

用一段话重申：拒付是第一条深链，统一案件、证据、规则、路由和审计才是平台底座。下一步是授权影子运行，而不是直接接管生产动作。

### 附录｜参考资料与验证入口

参考资料、固定提交、CI、仓库、飞书协作台和术语放在附录，保证正文连贯。

## 5. 表格替换规则

正文不再保留现有五张表格。替换方式如下：

- 参赛信息表 → 封面下方的项目名片；
- 官方评分映射表 → 四张评委导航卡；
- AI / 系统 / 人工职责表 → 三层纵向职责结构；
- 企业试点指标表 → 六张连续指标卡；
- 项目状态表 → 四个状态区。

只有真正需要横向比较且卡片无法表达的信息才允许保留表格。本版默认正文零表格，优先适配飞书窄屏阅读。

## 6. 现有图片重新排布

- 飞书协作台：放在 Demo 末尾作为跨团队协作延伸；
- AI 创新性对比图：放在创新性章节；

图片统一采用：

## 8. 事实与安全边界

- 案件与交易均为 Synthetic / Mock；
- 未接入 Oceanpayment 真实生产数据或资金动作；
- Evidence Readiness 不是胜诉概率；
- `UNVERIFIED_SUMMARY` 规则生产使用前必须由专家复核；
- 30% / 80% 是试点目标，100% 是设计硬约束；
- DeepSeek 的描述必须随固定提交、测试和真实运行证据更新；
- 生成图片只能表达概念和流程，不能伪造产品界面、客户收益或在线调用证据。

## 9. 实施与验收

实施只替换飞书正文，不修改产品代码：

1. 从现有正文提炼叙事型源稿；
2. 将五张表全部转换为卡片或纵向结构；
3. 按 Demo 五幕重新穿插 8 张真实图；
4. 替换飞书正文，保留现有文档链接和共享权限；
5. 搜索核验全部章节、图片、引用和状态词；
6. 确认无测试标记、图片占位符或能力夸大。

验收标准：

- 60 秒内可以复述项目定位、标杆链路和核心创新；
- 正文形成“问题—方案—运行—AI—价值—落地—证据”的连续逻辑；
- 正文零表格，飞书窄屏下不需要横向阅读；
- 8 张真实图均与对应 Demo 动作相邻；

- 飞书文档保持原链接并完成云端保存。
