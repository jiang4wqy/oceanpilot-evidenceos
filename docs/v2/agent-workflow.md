# V2 Agent 工作流

OceanPilot 的 Agent 围绕同一案件连续工作：业务动作成功后读取新版本，检查规则、证据与时限，生成有来源的处理计划和待确认提案；商户与 OP 可以在案件工作区追问原因，并由有权限的人执行下一步。每次运行、工具检查、提案和对话都保存在案件上下文中，刷新页面或重启服务后仍可追溯。

Agent 是两端共同使用的工作入口。它将“当前发生了什么、阻挡在哪里、由谁处理、确认后执行什么”放在一起，让使用者按案件计划推进。正式案件仍由 OceanPayment 运营；商户只在授权范围内决定和举证。

## 一次实际工作循环

1. OP 接收上游合成争议。Case Engine 提交案件和审计记录后，Agent 自动观察该版本，读取规则来源、材料清单和截止时间。
2. Agent 记录工具检查步骤，生成本案摘要及发布商户任务的提案。提案含具体任务文案、来源依据、责任角色和预期版本，等待 OP 确认。
3. OP 确认后，提案通过原有领域命令发布任务。Agent 再观察新版本，为商户展示规则允许的 Accept、Contest 分支；不会代商户选择。
4. 商户决定或补证后，Agent 按新快照更新缺口与下一步。用户可追问材料用途、规则依据、时限风险和责任人。
5. 材料齐备后，Agent 引导人工审核、证据包准备和最终确认。进入上游等待、资金核对或后续阶段时，继续按当前状态组织待办。

自动观察由成功的业务命令触发；“重新分析”可补齐缺失运行。当前没有后台定时轮询或自动发送商户消息，SLA 工具检查随案件版本和相应监控命令更新。

## 确定性工具与模型的职责

| 能力 | 实际执行者与依据 |
| --- | --- |
| 读取案件与商户范围 | Case Engine 与身份校验，使用已持久化的案件快照 |
| 规则、证据缺口、时限与角色 | 确定性规则和领域工具，保留来源及版本 |
| 可执行提案 | 根据当前状态和已确认权利生成；待输入信息列在 `required_inputs`，不臆造 |
| 对话解释、分析补充与草稿 | 配置后的模型 provider；实时模式使用 DeepSeek，测试可注入模型，离线模式明确标识 |
| 执行、终审、上游提交与资金核对 | 授权人确认后调用领域命令，继续经过权限、状态和 revision 闸门 |

业务动作后的即时观察运行先完成确定性工具检查，不等待模型网络请求。真人对话会实际调用已注入或已配置的 provider；在 `DEEPSEEK_LIVE` 模式下，接案、商户决定、材料登记/撤回、送审、结果与核对等关键业务事件还会排队触发后台模型解读，使用 `AUTO_EVENT` 来源标记。注入测试模型不会默认触发后台网络工作。模型输出用于表达、解释和草稿，规则引用、允许动作及状态判断仍由工具提供。运行与回答保存 provider/model 信息；确定性降级不得标作 DeepSeek 实时回答。

模型上下文包括经过脱敏的用户实际问题、已准备草稿、案件状态和工具依据。案件、商户、交易标识和证据对象位置不进入模型请求；敏感支付信息在调用前被拒绝。用户可以就同一材料或下一步继续追问，模型看到的是此次问题和该案的最小化上下文。

未配置实时模型时，可以完整运行确定性工具和流程。模型超时、失败或输出不适合使用时，Agent 返回带明确降级标记的工具摘要、来源和可用提案；不会因缺少模型回答而放开审核条件，也不会暴露 provider 错误中的内部细节。

材料就绪度只表示合成登记清单的完成情况。当前没有真实证据正文 OCR、真实性鉴定或经过企业历史数据校准的胜诉率模型。未知渠道规则、时限和操作权利仍需 OP 人工确认。

## 提案怎样推进业务

提案绑定 `case_id` 和 `expected_revision`，保存动作、具体输入、责任角色、理由与引用。需要人工补充的内容会明确列出；不能把空白输入自动补成业务事实。

确认操作提交提案 ID、唯一 `command_id`、当前预期版本和 `confirmed=true`。服务器从持久化提案读取真实动作和数据，客户端不能替换成别的命令。下列条件会阻止执行：

- 当前人没有该动作权限，或案件不属于该商户。
- 用户没有明确确认。
- 案件已变化，提案绑定的版本失效。
- 规则未确认、动作不在允许范围、关键材料缺失，或关闭条件尚未满足。

Accept/Contest、人审、最终提交和资金动作均保留原来的授权边界。Agent 不会自行确认商户责任、终审证据、提交真实上游、改动账本或关闭未核对案件。比赛版上游仍为 Mock/Disabled。

## 运行记录与失败恢复

每个案件版本最多保存一份工具观察运行，重复请求同一版本会复用运行与提案。实时模式中，显式“重新分析”可以追加模型解读，方便重试不可用的模型响应。活动记录包含最新运行、历史摘要、工具步骤、当前提案和对话；GET 仅查询，不调用模型、不写案件，也不隐式执行待办。

后台模型队列会合并同案的连续变化，优先分析最新版本。模型请求期间案件若已变化，旧回答不能保存为当前版本结论。普通事件重放不会重复调用模型；已持久化的自动解读在重启后也用于去重。队列本身不是持久任务系统，重启后需要显式运行恢复尚未完成的分析。

业务提交和 Agent 观察分开处理：命令先通过原有事务保存案件、revision、审计和幂等回执，再更新 Agent 活动。如果观察失败，已经成功的业务命令仍返回成功；界面可显示旧运行已过期，并通过“重新分析”恢复。重试原业务命令应复用 `command_id`，不会产生第二次业务效果。

Agent 运行记录用于解释与跟踪，不能替代 Case Engine 的业务审计。对话与重新分析本身不改变案件业务 revision；真正执行提案才会产生领域命令与相应审计。

## HTTP 接口

| 接口 | 输入及结果 |
| --- | --- |
| `GET /api/v2/cases/{case_id}/agent` | 返回 `run`、`history`、`proposals`、`summary`、`conversations`、`stale`；纯查询 |
| `POST /api/v2/cases/{case_id}/agent/run` | 输入 `expected_revision`；刷新或复用当前版本活动 |
| `POST /api/v2/cases/{case_id}/agent/messages` | 输入 `message`、`expected_revision`；返回回答、运行、来源、提案及实际 provider/model |
| `POST /api/v2/cases/{case_id}/agent/proposals/{proposal_id}/execute` | 输入 `command_id`、`expected_revision`、`confirmed`；返回原有业务命令结果 |

所有接口使用同一案件访问范围。运行记录与对话存入独立 Agent 表，应用在 lifespan 中初始化它们。当前 `X-Demo-*` 身份用于本地合成演示，不是企业生产身份认证。

接口回归位于 `tests/api/test_dispute_agent_api.py`，通过注入 `ScriptedModelProvider` 验证真实 provider 调用路径，完全不读取或使用真实 API 凭据。覆盖自动观察、GET 只读、同版本幂等、跨商户隔离、提案权限与陈旧版本、模型失败降级、已提交命令的观察失败恢复，以及重启后的运行和对话持久化。

后台并发回归位于 `tests/application/test_dispute_agent_events.py`，使用事件屏障控制模型执行，不依赖真实网络或固定睡眠。覆盖关键事件解读、同案变化合并、旧版结果丢弃、业务重放去重、重启后的自动解读去重，以及关闭后台模式时即时工具运行仍可用。
