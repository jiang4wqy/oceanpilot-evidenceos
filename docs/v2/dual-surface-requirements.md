# 双端独立案件体验：要求与验收清单

日期：2026-09-08。本轮实现已按下列条目验证；范围与证据见 [双端验收记录](dual-surface-acceptance.md)。参考 Stripe 官方公开资料，针对 OceanPilot 的角色、规则与合成演示边界作产品设计推导。

## 官方参考与采用范围

- [Stripe Disputes list](https://docs.stripe.com/connect/supported-embedded-components/disputes-list)：争议列表按案件呈现，选择一行进入该争议及关联付款详情，并支持筛选。用于定义“首页管理多案、案件页处理单案”的层次。
- [Respond to disputes](https://docs.stripe.com/disputes/responding)：先理解原因与投诉，再决定接受或抗辩，按案件需要准备材料，确认后提交，再跟踪审核结果。用于区分任务、草稿、审核与正式提交。Stripe 文档的期限、费用与文件限制不能直接作为 OceanPayment 生产规则。
- [Dispute evidence best practices](https://docs.stripe.com/disputes/best-practices)：材料按时间和类型组织，解释每项证明什么，只保留与投诉相关的内容。用于证据清单和 AI 草稿；不复制 Stripe 自有预测模型的胜诉概率。
- [Customer portal](https://docs.stripe.com/customer-management) 与 [Portal deep links](https://docs.stripe.com/customer-management/portal-deep-links)：面向客户的自助功能由业务配置，深链可让用户专注单项动作，并在完成后返回或看到确认。其业务是账单与订阅，此处仅参考任务入口与完成反馈，不声称它是争议商户门户。
- [How disputes work](https://docs.stripe.com/disputes/how-disputes-work)：争议阶段与上游结果需要持续跟踪。结合本项目已有资金规则，结果、终局性、资金核对和关闭保持独立。

## 五项设计原则

1. **首页找事，案件页办事。** 首页不自动选中第一案、不自动装载该案对话。案件使用可复制、可刷新、支持返回的独立 URL；页面标题、证据、提案、聊天始终绑定同一案件。
2. **双端按责任重组。** 商户提供交易事实、决定回应方式、补充材料；OceanPayment 核验规则、审核材料、正式提交、记录结果并核对资金。OceanPilot 在各自页面解释当前任务、准备文案和提案，动作仍由有权限的人确认。
3. **当前一步优先。** 案件页先回答“发生什么、何时到期、现在谁要做什么”；技术与审计明细渐进展开。商户看到补证引导，运营看到阻断原因与所需审核，不以同一组运营标签换标题实现双端。
4. **把准备、确认、提交和结果分开。** 商户按钮写“提交材料给 OceanPayment”；运营正式按钮写“确认向上游提交”。证据版本、审核人、冻结包和上游回执可追溯；完整度不能表达成胜诉率，WON 不能表达成资金已到账。
5. **同步要真实且不打断操作。** 业务事件更新案件后，两端自动同步同一 revision；确定性检查与异步模型分析各自显示实际状态和来源。刷新保留未发送文字和滚动位置，旧版本提案不能沿用，失败时明确最后同步时间与重试入口。

视觉方向沿用 OceanPayment 品牌，以浅色留白、清楚字号和单一主动作突出当前工作。Creative Production 的 Styles 参考要求保留既有品牌与事实，不为风格增加未经验证的指标、标签或产品能力。

AI 上下文以案件 ID、当前 revision 和访问角色为边界。面向商户的说明不得包含运营内部草稿或不可见记录；需要跨端传递的内容通过明确的协作/通知动作共享。不同案件的草稿、回答、流式结果和提案不得串案。无需为每案部署独立模型实例。

## 逐项验收

- [x] **H1 首页与详情分离：** 两端从根入口进入时只看到各自首页；点击案件进入独立 URL。复制地址、新标签打开、刷新、浏览器前进/后退均恢复正确页面，不自动跳到第一案。
- [x] **H2 双端有实质差异：** 商户首页与案件页围绕我的任务和材料；运营首页与案件页围绕队列、审核、提交和资金。商户不能通过界面或接口处理其他商户案件及运营动作。
- [x] **C1 抗辩/补证：** 商户明确选择 CONTEST 后，材料按核验规则生成清单；登记/撤回立即重算缺口；缺关键证据时明确阻断提交材料，不把未响应自动转换为接受。
- [x] **C2 审核/正式提交：** 商户提交材料后进入待运营审核；风控可退回并说明原因，商户看到需要修改的具体项目；审核通过、冻结与主管确认后才允许运营正式提交，且显示确认内容与回执。
- [x] **C3 结果/资金：** 上游结果及新阶段分别记录；WON 但资金差异时仍保持待核对，商户看到“结果已确认，资金仍在核对”；对账、通知与关闭各自遵守权限和条件。
- [x] **A1 每案独立 AI：** 在案件 A 提问后切到 B、后退回 A、刷新和更换角色，回答、草稿、提案及来源仍归属正确案件/可见角色。无案件时不显示伪造的已完成分析。
- [x] **A2 AI 有业务差异：** 同案商户问“下一步”得到可完成的材料/决定指引；运营得到审核/提交/资金建议。建议引用当前状态与缺口，回答由谁确认，并以实际 MODEL/FALLBACK/DETERMINISTIC 元数据标记来源。
- [x] **A3 人工确认：** 保存的提案执行前展示数据及影响；要求确认的复选框默认不勾选。编辑字段或补充必填值走普通命令；owner、revision 不符时失效并更新计划。
- [x] **S1 双向自动同步：** Chrome 商户页与另一浏览器/独立上下文的运营页同时打开同案；商户补证、运营退回/评论两向传播，无需手动刷新。记录从成功回执到另一端显示相同 revision 的时延，前台目标不超过 3 秒；若采用其他预算，验收记录需明确实测值。
- [x] **S2 模型异步状态：** 补证后先显示实际工具观察，再显示真实模型后台分析；pending 结束自动出现对应 revision 的回答。等待期间仍可阅读和输入，不虚构工具动作或模型思维过程。
- [x] **S3 断线与并发：** 恢复连接/返回前台后自动追平；同步中的输入不丢失。另一端推进版本时，本端已打开的旧确认框不能提交陈旧提案；不重复业务命令。
- [x] **V1 可读与可用：** 案件页主要任务、金额、截止时间、AI 输入在桌面与手机可辨认；关键正文至少 12px；移动端无页面横向溢出，长聊天和引用可独立滚动，加载/空态/错误均有真实反馈。

验收只使用合成案例和模拟上游；真实模型接入状态必须取运行时返回值。上述条目不赋予外部系统发信、生产提交或绕过权限的授权。
