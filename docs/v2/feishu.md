# V2 Feishu collaboration adapter

The V2 adapter connects verified Feishu callbacks to the same dispute commands,
merchant scope, revision checks and audit trail used by the portals. It supports
merchant Accept/Contest and case-specific `@OceanPilot` summary requests. It never
creates a formal dispute from a chat message.

The competition boundary remains explicit: cases use synthetic data, upstream
submission is Mock, and outbound Feishu delivery is Disabled. No real tenant smoke
test or message delivery has been performed for this implementation. Passing local
tests establishes callback and command behavior, not tenant deployment readiness.

## Endpoints and application wiring

| Endpoint | Behavior |
| --- | --- |
| `POST /api/v2/integrations/feishu/events` | Signed URL verification and `im.message.receive_v1` callbacks |
| `POST /api/v2/integrations/feishu/card` | Signed `card.action.trigger` callbacks |

Include `oceanpilot.api.dispute_feishu.router` in the application. Inside FastAPI
lifespan, after the dispute service exists, call:

```python
initialize_dispute_feishu(
    app,
    db_path=Path("data/dispute-feishu.db"),
    base_url="https://your-application.example",
)
```

The initializer must run in lifespan: constructing the application must not open a
database. Missing or invalid trusted configuration leaves the adapter disabled;
both callback endpoints then return `503 FEISHU_V2_DISABLED`. No outbound client
is constructed, and no environment setting enables external sends.

## Trusted identity and merchant bindings

Configuration is operator-managed. Never derive roles or merchant ownership from
card values, message text, query parameters, or a callback user's assertions.

Required environment variables:

- `FEISHU_ENCRYPT_KEY`: used by the existing request-signature verifier.
- `FEISHU_VERIFICATION_TOKEN`: verified on every payload, including URL challenges.
- `OCEANPILOT_V2_FEISHU_BINDINGS_JSON`: JSON object containing `actors` and `chats`.

Binding keys are generated by the exported `binding_key(kind, tenant_key,
external_id)` helper. Actor keys combine the tenant key and sender/operator
`open_id`; chat keys combine the tenant key and chat ID. Stored references use
SHA-256 with domain separation. Hashes minimize raw identifier storage; they are
identifiers, not authentication credentials. Signature and token verification
remain mandatory.

Generate a **synthetic example**, without real secrets:

```python
import json
from oceanpilot.adapters.channels.feishu.v2 import binding_key

bindings = {
    "actors": {
        binding_key("actor", "synthetic-tenant", "synthetic-open-id"): {
            "role": "MERCHANT",
            "actor_id": "merchant-demo-user",
            "merchant_id": "merchant-demo",
        },
    },
    "chats": {
        binding_key("chat", "synthetic-tenant", "synthetic-chat-id"): "merchant-demo",
    },
}
print(json.dumps(bindings))
```

Allowed binding roles are `MERCHANT`, `OPERATOR`, `RISK_OFFICER`, `SUPERVISOR` and
`AGENT`. Only `MERCHANT` can invoke Accept/Contest. Governance `ADMIN` does not
implicitly gain business permissions. Every binding also has an explicit merchant
scope; the actor's scope must equal the chat's scope and the actual Case owner
merchant. Add separate trusted identities when a business operator requires a
different merchant scope. Unknown actor/chat/tenant mappings fail closed.

## Cards and merchant decisions

`app.state.dispute_feishu.render_case_card(...)` renders a local card for a trusted
chat. It makes no network request and must not be described as delivered:

```python
card = app.state.dispute_feishu.render_case_card(
    case_id,
    authorized_identity,
    tenant_key="synthetic-tenant",
    chat_id="synthetic-chat-id",
    kind="NEW_DISPUTE",
)
```

Supported kinds are `NEW_DISPUTE`, `MISSING_EVIDENCE`, `SLA_REMINDER`,
`REVIEW_FEEDBACK` and `SUMMARY`. Cards include the case reference, current plan,
synthetic/Mock/Disabled labels and a portal deep link. Only a new dispute card can
carry Accept/Contest buttons. The buttons include an explicit Feishu confirmation
dialog and a strictly boolean `confirmed` value; the command service independently
enforces merchant authorization, current state and revision.

Every locally rendered card creates a random opaque `card_ref` in the adapter
database, bound to Case ID, revision, tenant-scoped chat, merchant and one-hour
expiry. Callbacks select the server record using that reference. Card-supplied
roles, merchant IDs and revisions never confer authority. A conflicting supplied
Case ID is rejected. Old revisions, expired references, foreign chats and unknown
references cannot change the case. Card references can represent multiple cases
within one persistent merchant collaboration space.

Decision callbacks execute exactly one `MERCHANT_DECISION` command. Its `data`
includes `channel=FEISHU`, a hashed external event reference and a hashed thread
reference. The Case Engine atomically records the decision, collaboration event
and audit; the adapter does not append a second, non-atomic comment.

## Agent entry and callback responses

Send a text callback in the form `@OceanPilot CASE_ID 还缺什么？`; Feishu's rendered
mention marker `@_user_1 CASE_ID ...` is also accepted. An explicit Case ID is
required because a chat may contain several cases. The adapter validates case
ownership, records one `COMMENT` command with `channel=FEISHU`, and returns the
deterministic `case_plan` in the callback response. This summary does not invoke
an external model and cannot authorize a business transition. Bot messages,
unrelated text and unsupported event types create no cases or commands.

Successful callbacks return the case reference, recorded revision, case plan and
`outbound_delivery=DISABLED`. The JSON response is a local integration seam; it is
not proof that Feishu displayed an Agent reply or a card. A future authorized
delivery adapter must explicitly map the result to Feishu messaging/card update
APIs, handle delivery receipts and preserve the same Case audit context.

## Request and retry guarantees

- Requests are capped at 64 KiB and require JSON content type.
- The existing `FeishuRequestVerifier` checks SHA-256 signature, token and a
  300-second timestamp window before parsing a business action.
- Receipt IDs combine tenant and event ID. Reusing one event ID with a changed
  payload is a `409` conflict, including changes of actor or requested action.
- The first accepted callback stores its command before execution. The command
  ID is deterministic; retries use the original expected revision and data.
- Completed callback responses replay from SQLite without a second domain write.
  If the Case commit succeeds but receipt completion fails, retrying uses the
  same idempotent domain command and then completes the response receipt.
- No raw callback body, verification token or encryption key is stored. External
  actor and chat IDs are replaced with binding/audit references. User-authored
  message content passes the existing sensitive-data validator before callback
  command persistence, and remains subject to Case Engine validation.
- All error responses use `application/problem+json`; verification and unexpected
  failures return fixed codes without callback content or exception details.

Local coverage is in `tests/channels/test_dispute_feishu.py`: trusted binding,
signed request rejection, confirmation, stale revision, cross-merchant access,
card kinds, case summaries, restart replay and interruption recovery. Run with:

```bash
PYTHONPATH=src .venv/bin/pytest tests/channels/test_dispute_feishu.py -q
```

## Tenant integration still to validate

Real tenant validation requires administrator-provisioned actor/chat bindings,
the intended application event subscriptions and permissions, a reachable HTTPS
callback URL and verification settings. Validate actual event/confirmation
payloads and delivery behavior against that tenant before describing Feishu as
live. Encrypted-body callbacks are not decrypted by this adapter; they fail
verification. Existing cryptographic support covers signed plaintext JSON only.
None of these deployment checks authorizes sending messages to real recipients.
